## Context

`/eval` currently owns analysis, HTML persistence and presentation in one function. After a successful CHIEF run it writes both run-local `output/dashboard.html` and the compatibility `~/.dscode/eval/<prefix>.html`, then unconditionally invokes the OS browser. This is correct for TUI, but WebUI receives only text progress through `ui.addInfo`.

WebUI already renders self-contained HTML through `ArtifactContainer` with `iframe.srcDoc` and `sandbox="allow-same-origin"`. That component currently represents an LLM-generated Session Dashboard: `artifact_start/delta/end` accumulate mutable HTML, `MessageInput` updates it through another model call, and `dscode-dash-cache` keys it by current Session content hash. Reusing those semantics unchanged would let an Eval report overwrite the Session Dashboard cache and expose a misleading “edit report” input.

UI notifications are intended to flow through `HarnessEventBus`; `UiBackend` deliberately contains only lifecycle and permission request methods. The integration therefore must not add Eval-specific methods or backend type checks to `UiBackend`.

## Goals / Non-Goals

**Goals:**

- Display the exact persisted CHIEF HTML inside WebUI without a second model call.
- Switch WebUI into Eval mode immediately when its prompt submits `/eval`, before slow CHIEF work starts.
- Project Eval starting/running/completed/failed lifecycle through typed shared events.
- Keep the entire Eval main area focused on preparation, progress, report or failure content.
- Preserve target Session and run identity when evaluating a historical Session.
- Keep Eval reports read-only and isolated from Session Dashboard state/cache.
- Preserve existing TUI external-browser behavior and output paths.
- Reuse the existing sandboxed iframe and warm WebUI shell.

**Non-Goals:**

- Do not convert CHIEF HTML into React components.
- Do not expose `~/.dscode/eval` through a generic static-file route.
- Do not make Eval HTML editable through the Session Dashboard artifact pipeline.
- Do not append Eval HTML or worker output to Main Agent messages.
- Do not redesign the CHIEF report contents in this change.
- Do not add a server-side report browser or historical run list.

## Decisions

### 1. Publish a domain lifecycle event; keep presentation out of `runEval`

Add a `HarnessEvent` such as:

```ts
type EvalDashboardState =
  | {
      status: "starting";
      requestedSessionId?: string;
      targetSessionId?: string;
    }
  | {
      status: "running";
      targetSessionId: string;
      runId: string;
      stage: ChiefStage;
      index: number;
      total: number;
      application: string;
      workerAgentId?: string;
    }
  | {
      status: "completed";
      targetSessionId: string;
      runId: string;
      html: string;
      outputPath: string;
      generatedAt: number;
    }
  | {
      status: "failed";
      targetSessionId: string;
      runId?: string;
      stage?: ChiefStage;
      error: string;
    };
```

The `/eval` command handler SHALL emit `starting` synchronously, before awaiting Session loading or any other asynchronous operation. `runEval` SHALL then emit `running` after the target is frozen/run is created and on every CHIEF stage update, followed by `completed` or `failed`. TUI subscribes to the completed event and calls `openDashboard(outputPath)`. WebUI maps the same domain event to a typed WebSocket `eval_dashboard` event.

This ordering guarantees:

```text
Web prompt submits /eval
        │
        ├─ emit starting ───────────────▶ WebUI enters Eval immediately
        │
        ├─ resolve/freeze target
        ├─ emit running(stage=prepare) ─▶ target/run metadata + timer
        ├─ emit running(stage=N) ───────▶ worker/retry/progress updates
        └─ emit completed|failed ───────▶ report or failure state
```

This keeps the four-method `UiBackend` contract unchanged and avoids `instanceof WebUiBackend` or constructor-name checks.

Alternative considered: add `showEvalDashboard()` to `UiBackend`. Rejected because it reintroduces notification methods into an interface intentionally reduced to lifecycle and blocking permission requests.

### 2. Send validated HTML, not an arbitrary file URL

The completed event carries the HTML generated by the coordinator for the known run. WebUI sends that string over its existing WebSocket and renders it through `srcDoc`.

The backend SHALL NOT accept a client-provided path and SHALL NOT serve `~/.dscode/eval` as a static root. The explicit external-open action in WebUI creates a Blob URL from the already received HTML. TUI continues to open the persisted compatibility file.

Alternative considered: add `/eval/*` static routes. Rejected because path validation, authorization and lifecycle become broader than this feature requires.

### 3. Model Eval as a third view, not a subtype of mutable Dashboard

Introduce:

```ts
type ViewMode = "chat" | "session_dashboard" | "eval_dashboard";
```

- `session_dashboard` retains current generation, cache, transition animation and pure-instruction update behavior.
- `eval_dashboard` owns the whole main area and displays only Eval preparation, stage progress, report or failure content around the shared iframe.
- `MessageInput` is not rendered in `eval_dashboard`; a read-only footer explains that the report cannot be modified.
- `session_dashboard` has one legal entry edge: an explicit Dashboard selection while the active mode is a non-empty `chat`. Eval disables the Dashboard selector. The App handler repeats the same source-mode guard, and transition completion checks that Chat is still active before committing, so neither a programmatic mode request nor a stale Chat → Dashboard animation can enter from Eval.
- Chat, Dashboard and Eval are always rendered as shell-level controls. Clicking Eval sends the existing `{ type: "slash", command: "/eval" }` command when state is absent or terminal (`completed`/`failed`), including a `completed` state restored from cache. It does not introduce a new client protocol or fabricate local lifecycle state; the authoritative synchronous `starting` event activates the new run. Only `starting`/`running` are treated as an in-flight run, in which case clicking Eval is pure view navigation and does not start a concurrent duplicate.
- Chat and Dashboard remain navigation destinations in the header, but the Eval prototype SHALL NOT render mock Chat or Session Dashboard content inside the Eval area.
- Chat → Session Dashboard keeps the existing cluster transition. Eval switches directly on the synchronous `starting` event because it is an operational command result, not an alternate rendering of the conversation.

Changing the current Session resets `session_dashboard` to Chat, but does not silently rewrite or retarget an open Eval report. Eval metadata always names its own target Session.

### 4. Keep Session and Eval caches physically separate

Retain `dscode-dash-cache` unchanged for generated Session Dashboards. Add `dscode-eval-dash-cache` entries keyed by `${targetSessionId}:${runId}` with:

```ts
interface EvalDashboardCacheEntry {
  formatVersion: number;
  targetSessionId: string;
  runId: string;
  generatedAt: number;
  html: string;
}
```

Eval entries are immutable by run ID, bounded to the five most recently accessed reports, and only written on `status: "completed"`. Running and failed events never replace successful cached HTML. The latest received Eval artifact remains selectable even when its target is not the current Session.

Five entries limit localStorage pressure while preserving recent diagnostics. Durable history remains in `~/.dscode/eval/<target>/runs/`.

### 5. Reuse `ArtifactContainer` with an explicit presentation descriptor

Extend `ArtifactContainer` with a descriptor rather than duplicating iframe logic:

```ts
interface ArtifactPresentation {
  kind: "session_dashboard" | "eval_dashboard";
  html: string;
  loading: boolean;
}
```

The iframe sandbox remains `allow-same-origin` without `allow-scripts`; generated Eval HTML is self-contained and does not require script execution. Eval-specific toolbar, progress, failure and read-only footer live outside the iframe so they use WebUI design tokens and remain accessible.

The Eval content slot between toolbar and footer SHALL itself be a `min-height: 0` column flex container. `ArtifactContainer` is then a flex item that consumes the remaining height, for both Completed and failed historical-report presentations. Without this parent flex context, the iframe's `flex: 1` is inert and the browser falls back to its intrinsic approximately 150px height, leaving the rest of the Eval surface blank.

### 6. Treat slow CHIEF execution as a first-class Eval screen

`starting` renders target resolution/freeze preparation. `running` renders:

- target Session and run ID
- elapsed wall time
- actor, Step and evidence summary once available
- all seven CHIEF stages with completed/current/pending state
- active worker Application and 6-character Agent ID
- validation attempt/retry count

The frontend SHALL derive these values from structured lifecycle payloads rather than parsing `ui.addInfo` strings. It SHALL keep the previous completed HTML hidden until the current run completes; partially generated files are never streamed as a report.

Starting, Running and Failed use a full-surface lifecycle layout: the outer container takes the same available main-area bounds and 16px gutter as ChatView, while its internal summary, worker and stage regions expand responsively. A fixed `max-width` centered card is rejected because it underuses the WebUI workspace on desktop.

### 7. Preserve and automatically show the same target's latest complete report on failure

On a running event, WebUI switches to Eval view and displays stage progress. On completion, it atomically replaces the running panel with the HTML and writes the Eval cache. On failure, the active lifecycle remains `failed`; the frontend looks up the newest completed cache entry whose `targetSessionId` exactly matches the failed run. If one exists, it automatically renders that immutable historical HTML below a failure notice identifying the failed stage, current run and historical report run. If none exists, the main area remains a blank failure surface with diagnostics and recovery actions.

Selection uses `generatedAt`, not LRU access time, so opening an older report does not make it the semantic latest success. A successful report from another target Session MUST NOT be rendered or offered as fallback. Failed events never write HTML, never replace cache entries and never become `completed`.

### 8. Resolve switch targets from project and global indexes

The Web sidebar is populated from the current project's Session index, while the compatibility global index is capacity-limited. Resolving `switchSession()` only from `listAllSessions()` can therefore reject a Session that remains visible and valid in the current project.

Target preflight SHALL build one candidate map from `listSessions()`, `listAllSessions()` and current Session metadata, deduplicated by full Session ID. Prefix matching and ambiguity checks run against that union before abort, save or mutation. This preserves cross-project compatibility while making the current project index authoritative for its own Sessions.

Alternative considered: remove the global index cap. Rejected because it changes storage retention and lookup cost beyond this fix. Alternative considered: let the Web adapter pass a file path. Rejected because target resolution belongs in the shared UI-independent switching transaction.

## Risks / Trade-offs

- **[Starting event is delayed behind Session I/O]** → Emit synchronously in the slash-command path before the first `await`, then enrich identity in the first running event.
- **[Large HTML increases WebSocket/localStorage usage]** → Send only once on completion, bound Eval cache to five entries, and keep persistent history on disk.
- **[Historical target is confused with current Session]** → Display target short ID and run ID outside the iframe; never derive Eval identity from `currentSessionId`.
- **[Session Dashboard behavior regresses during view-mode rename]** → Define a shared `ViewMode` type and add focused tests for cache hits, transitions, MessageInput routing and empty-session behavior.
- **[Failure event arrives after a later run starts]** → Compare `runId` before applying lifecycle updates; stale events may update cache by identity but SHALL NOT replace the active Eval view.
- **[Web iframe executes generated script]** → Preserve the existing sandbox without `allow-scripts`.
- **[All connected Web clients see a command result]** → Keep current WebBackend broadcast semantics; target identity is included so every client renders the same authoritative run.
- **[Project/global indexes contain the same Session]** → Deduplicate candidates by full Session ID before prefix matching so duplicate metadata cannot create false ambiguity.

## Migration Plan

1. Add typed domain and WebSocket Eval Dashboard events with no consumers; existing behavior remains unchanged.
2. Add frontend `ViewMode`, Eval state/cache and presentation components while keeping Session Dashboard tests green.
3. Make the Web `/eval` command path emit `starting` synchronously; make `runEval` emit enriched lifecycle events and move external opening into the TUI event subscriber.
4. Enable WebBackend projection and automatic Eval view switching on `starting`.
5. Verify current Session, historical Session, completion, failure, stale-event, reload-cache and TUI compatibility paths.

Rollback removes the new event subscriptions and restores `openDashboard()` to the successful `runEval` path. Persisted HTML and existing Session Dashboard cache require no migration.

## Open Questions

- The first version retains only five Eval reports in browser cache. A future Eval history panel can read durable run manifests instead of increasing localStorage retention.
